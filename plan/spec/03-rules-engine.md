# Spec 03 — Rules engine

The rules engine turns `core` + active stack packs + project customizations into one rulebook with stable IDs, writes it into the project as native Claude Code rules, and answers "which rules apply to this diff" for the reviewer.

## 1. Sources and layering

1. **core** (always active).
2. **Stack packs** in the order: `requires` first (topological), then profile order. For each pack: base `rules.md`, then the chosen variant's rule file (a variant rule with the same ID replaces the base rule).
3. **Project**: files listed in `rules.add`, then `override`, `extend`, `disable` from the profile.

Errors (build fails, exit 1):
- Duplicate rule ID across different packs or project files.
- `override`/`extend`/`disable`/`options` naming an unknown ID.
- Disabling or overriding a `protected` rule without `allowProtected: true` and a reason.
- Unresolved placeholder.
- Scope `areas:x` where no package has area `x` → **warning**, rule kept as global-inactive (listed in the lock as `inactive`, not written).

## 2. Customization semantics

| Operation | Effect |
|---|---|
| `add` | Parse like pack rule files. Project IDs should use a project prefix (`FISKO-…`); `cw rules build` warns otherwise |
| `override[ID] = file` | If the file starts with a rule heading for the same ID, it replaces title, meta and body; otherwise it replaces the body only. The lock records `modified: "override"` |
| `extend[ID] = text` | Appends a paragraph `**Project addition:** <text>` to the body. `modified: "extend"` |
| `disable[{id, reason}]` | Removes the rule; listed in the global file's footer "Disabled in this project: ID (reason)" so reviewers know |
| `options[ID]` | Values for `{ruleOptions.x}` in that rule |

## 3. Scope resolution

| Scope | Resolved globs |
|---|---|
| `all` | none (global) |
| `areas:a,b` | for each package with any of the areas: `<path>/**` for each of its paths |
| `paths:g1\|g2` | the globs after placeholder resolution, relative to the repo root |

## 4. Output files

Directory `.claude/rules/workflow/`. Files carry the marker line `<!-- Generated by dev-workflow (cw rules build). Do not edit. -->`; `rules build` deletes stale files in that directory only if they carry the marker.

Grouping:
- Global rules → `00-global.md` (no frontmatter).
- Area-scoped rules → one file per distinct area set: `area-<areas sorted, joined by '-'>.md`, frontmatter `paths:` = resolved globs.
- Path-scoped rules → one file per distinct glob set: `paths-<first pack id>-<n>.md`.

File layout:

```markdown
---
paths:
  - "fisko-app/**"
---
<!-- Generated by dev-workflow (cw rules build). Do not edit. -->
<!-- Sources: core@1.0.0, react-vite@1.0.0 (react-18), tailwind@1.0.0, project -->

# Workflow rules — frontend

## REACT-A11Y — Accessibility · blocking
<body>

## FISKO-UI-COPY — Copy and formatting · blocking · protected
<body>
```

`00-global.md` starts with the preamble (from the old CQ preamble, generalized):

> These rules apply to every change in this repository, made by people or agents. They cover new and changed code; don't rewrite untouched code just to comply. Reviewers check every applicable rule and cite its ID in findings. If a rule conflicts with an explicit requirement in the task spec, the spec wins, except for rules marked **protected**, which a spec can't override. State any deviation in the report. `cw rules applicable --task <id>` lists the rules that apply to a task's diff.

Ordering inside a file: core, packs in layering order, project; within a source, file order.

Size: a file over 12 KB prints a warning (context cost).

## 5. Lock and drift

`rules build` writes `.claude/workflow/rulebook.lock.json` (spec 01 §12). `rules build --check` recomputes in memory and compares with the files on disk and the lock:
- Prints added, removed and changed rule IDs, changed plugin/pack versions, and hand-edited output files (hash mismatch).
- Exit 1 on any difference. The SessionStart hook reports it; it never rewrites.

## 6. Queries

| Command | Behaviour |
|---|---|
| `cw rules list [--json]` | All active rules: ID, title, source, scope, severity, protected, modified |
| `cw rules show <ID\|alias>` | Full text of one rule; aliases (`CQ-12`) resolve via the lock |
| `cw rules applicable --task <id> \| --base <sha> [--json]` | Changed files (as in `cw checks --changed`) → every global rule plus every scoped rule whose globs match at least one changed file. Output sorted by layer; JSON includes the full text so the reviewer needs no second call |

## 7. Glob semantics (`lib/glob.mjs`)

- `**` matches zero or more path segments; `*` any characters except `/`; `?` one character except `/`; `{a,b}` alternatives (nesting allowed); `[abc]` classes.
- Dotfiles match (`**/*.yml` matches `.github/workflows/x.yml`).
- Patterns and paths are POSIX, repo-relative; a trailing `/` in a pattern means "directory and below".
- Unit tests include the globs used by every base pack.

## 8. Tests

- Golden test: fisko fixture profile → expected output files and lock (checked in under `tests/golden/fisko-rules/`).
- Mapping test (WP-57): every alias in the lock covers the old IDs CQ-1…CQ-28 (fisko) and CQ-1…CQ-23 (`claude-workflow` rulebook, with an `express@5`/`react-19` fixture profile); the test lists any old ID without a successor.
- Error cases from §1, one test each.
- Drift: change a pack rule in a temp plugin copy → `--check` exits 1 and names the ID.
